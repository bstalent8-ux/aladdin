**Model, in one line each.** A notification belongs to a **person** — `organization_id` is context and must never reach a `USING` clause. A conversation is a property of a **transaction** — it is anchored to an `rfq`, `quotation` or `order`, both party organizations are derived from that record, and **no RPC accepts an organization id**. Chat access is `active membership + conversation.participate` in one of the two party orgs, so a colleague holding the capability reads the whole thread; there is no participant list and no way to start a conversation with a person.

**`message.sent`** is emitted by `send_message` in the same transaction as the message insert, to the **opposite** party only, via `app.notify_org` with `conversation.participate`. It deep-links to the underlying record, carries `counterparty_name` and **never the message body**, and is the one event with the `org.manage` owner fallback **disabled** — an owner without the capability cannot open the thread, so is never told one exists. Where the counterparty has no holder, nobody is notified and the message still persists. No dedupe, grouping or digest in the Pilot (chat-core.md Q6, decided).

**Application / UI.** Notifications: one `notification-list` serving the header panel and the supply dashboard, real counted badge, `router.refresh()` reconciliation. Chat: caller-scoped query layer (`server/queries/chat.ts`), RPC-only mutation layer (`server/actions/chat.ts`), view models, a bounded recent conversation list and the thread **inside the existing header Chat panel** — there is deliberately **no `/chat` route** — plus one entry point each on the RFQ, quotation and order detail pages. `project` is not a chat subject; a project uses its parent order's conversation.

**Deliberately absent:** Realtime (no table joined `supabase_realtime`), Points, attachments, message edit/delete, reactions, typing, presence, read receipts, notification preferences, and any consumer/personal DM model.
