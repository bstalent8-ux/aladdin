## Concrete Supabase Free proposal — no settings applied

These controls reduce risk; **they do not guarantee an aggregate per-account password-attempt limit across IP addresses at GoTrue**. The owner must explicitly accept the residual risks before this weaker alternative can replace the strict merge blocker. Approval of local test isolation is not approval of that security tradeoff.

| Layer | Proposed initial configuration / responsibility |
|---|---|
| Native bot control |Enable Turnstile in Supabase Auth only after the CAPTCHA task's compatible app is tested and deployed under a separately approved rollout. Separate real staging/production widgets with exact hostname allowlists; no wildcard preview/test widget on production. No test secret outside local. Native challenges cover supported password/signup/recovery endpoints, including direct GoTrue calls.|
| Application challenge compatibility |One token, one verifier. Native Auth paths forward fresh `options.captchaToken` and do not pre-consume it with Siteverify. Privileged phone registration/Admin API remains protected by app Siteverify tokenA with action/hostname checks; its subsequent native login uses a separate tokenB. Refresh on expiry/retry, neutral errors and fail-closed handling. Preserve registration rollback/quarantine if session bootstrap fails. CAPTCHA owner supplies this work.|
| Native IP limits |Start with current staged values: **token endpoint150requests/5min/IP, burst30**; other signup/recovery/resend/OTP request bucket30/5min/IP; verify30/5min/IP. Keep same-user resend/recovery cooldown60seconds where supported. Do not blindly reduce the token budget because it also covers refresh, password, PKCE and ID-token grants.|
| App phone/IP limits |Retain existing atomic15minute budgets: login10/normalized-phone and30/IP; registration5/phone and10/IP. Shared Installer/Showroom HMAC buckets, private grants, bounded retention and trusted edge IP extraction. Count attempts, fail closed when unavailable; preserve generic failures and explicit limited/retry UI. These limits cover application calls only.|
| Server-side IP forwarding |Leave hosted forwarding unchanged pending a trusted-ingress/load test. SSR requests can share the server's source IP and unexpectedly exhaust the native token budget. Any later forwarding change requires separate review/approval, supported modern secret-key handling and proof untrusted callers cannot choose the budget IP. Never expose privileged keys to browsers.|
| Sessions and authorization |No UUID/password/session migration, no OAuth/OTP expansion and no role changes. Preserve expiry/refresh/logout behavior, cookie/origin controls, server account-type checks, RLS, tenant boundaries and admin approval/address rules.|

**Important rate-label clarification:** the dashboard label “token refreshes150” must not be interpreted as refresh-only, nor its “sign-ups and sign-ins30” as a30-attempt password-grant guarantee. `/auth/v1/token` has its own shared grant budget. These are staged observations plus the current documented endpoint mapping; production values remain unverified. [Native limits and forwarding](https://supabase.com/docs/guides/auth/rate-limits).

Supabase supports native Turnstile; app-only validation does not enable it. Tokens expire after300seconds and are single-use, so double verification is incompatible. [Supabase CAPTCHA](https://supabase.com/docs/guides/auth/auth-captcha), [Turnstile validation](https://developers.cloudflare.com/turnstile/get-started/server-side-validation/).

### Logging, monitoring, alerts and cost

Proposed app events: timestamp, opaque request ID, account kind/action, coarse outcome (`success`, `credentials`, `captcha`, `limited`, `unavailable`), status and duration. Aggregate app counters without logging phones, internal aliases, raw IPs, passwords, tokens, cookies, request bodies or provider internal errors. Keep raw provider logs restricted; export only sanitized counts. Do not treat `auth.audit_log_entries` as an atomic failed-password counter. Use Auth service/request logs for direct endpoint failures; verify actual failed-request coverage before rollout. [Audit logs and delay](https://supabase.com/docs/guides/auth/audit-logs).

Proposed initial alert rules, to tune using isolated baseline traffic: auth5xx/unavailable>=5in5min; app quota denials>=20in5min; native token429>=10in5min; CAPTCHA failures>=20and>50%of attempts in5min. Notify one named security owner using an explicitly approved existing alert channel, deduplicate30minutes and include project/environment and aggregate counts only. No automated account suspension or global CAPTCHA disablement. The responder reviews distributed failures, verifies service health/hostname/key rollout and applies only separately approved mitigation. Any emergency weakening of CAPTCHA must be an explicit owner incident decision, not automatic rollback.

Automated provider alert collection/delivery is **not currently implemented or verified**. Proposed app event alerts can reuse an approved existing monitoring integration if available; if none exists, obtain approval for a small sanitized collector/destination and its actual scheduler/budget before rollout. No broad new Management API token or paid log drain is assumed. Manual restricted dashboard review can support a supervised pilot, but does not provide timely automated direct-GoTrue alerts. Do not claim it is equivalent. Alert coverage/ownership is a release gate, or a separate explicitly accepted supervised-pilot limitation.

Subscription increment for Supabase Free + Turnstile Free: **$0**; implementation, existing hosting/SMTP/alert transport, quota consumption and operator time are not zero-cost guarantees. No new paid service, monitoring subscription or purchase is proposed as already approved. Turnstile Free supports production use and unlimited challenges. Native log retention/quotas limit forensic visibility; current Supabase docs describe1GB Free ingest and upcoming query/retention enforcement beginning2027. Avoid continuous broad log polling and recheck plan entitlements before implementation. [Turnstile plan](https://developers.cloudflare.com/turnstile/plans/), [logs ingest](https://supabase.com/docs/guides/platform/manage-your-usage/logs-ingest), [query policy](https://supabase.com/docs/guides/platform/manage-your-usage/logs-query).

### Rollout sequence and existing-account impact

After separate approval: identify production correctly; complete local isolated acceptance and CAPTCHA-owner handoff; verify real widget keys/allowlists, log/alert coverage and controlled staging smoke; apply approved schema batch before compatible app promotion; deploy the CAPTCHA-ready app before enabling the native toggle; then enable native protection and verify legitimate and direct-negative flows. None of these hosted steps is performed in this task.

Installer and Showroom retain the same internal aliases, password hashes, UUIDs, roles and standard SSR sessions. General email auth, resend/recovery/OTP, password reauthentication and employee-invitation continuations must also be covered by the CAPTCHA handoff. Enabling native CAPTCHA before that compatibility is established can lock out existing users. Test shared-IP/refresh traffic and accessibility; successful synthetic test keys do not prove real replay/expiry/hostname or provider-outage behavior. Do not silently downgrade native CAPTCHA during rollback; prefer a CAPTCHA-compatible application rollback with the schema's old RPCs still available.

## Explicit residual risks and strict alternative

Owner acceptance would still be needed for distributed guesses with solved/relayed challenges; low-rate password spraying and credential stuffing; direct GoTrue calls bypassing app buckets; successful use of already compromised credentials; temporary legitimate-user denial from phone buckets/shared-IP limits; CAPTCHA/accessibility/provider outages; incomplete/delayed logs or alert gaps. Native error/OTP enumeration remains a provider-side concern. Monitoring is reactive and cannot replace synchronous account enforcement.

If the original strict guarantee remains mandatory, Free defense-in-depth is **insufficient**. The least disruptive separate proof is a disposable, synthetic-only evaluation of the existing open-source GoTrue engine behind an exclusive private upstream and an atomic account/IP ingress budget. Prove direct-origin/alternate-route denial, distributed/concurrent limits, UUID/hash/session/JWT/RLS/Storage/Realtime compatibility and recovery/availability behavior before estimating operations cost. It must not migrate real identities, replace hosted Auth or purchase infrastructure. Even this proof needs a separate approval; a paid post-verification hook and another provider are not implemented alternatives. See [prior decision research](showroom-auth-provider-security-options.md).
